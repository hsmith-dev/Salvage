## Intent

**Problem:** FR-7/FR-8: when metadata is gone, reconstruct files from raw bytes by signature, automatically during the normal scan, with Medium/Low confidence only (AD-7) and declarative JSON signatures (AD-6). FR-8 / Story 3.2: reconstructed files get collision-free generated names under `Reconstructed/<type>/`, and partial carves are marked, never shown as complete.

**Approach:** `ScanSession` already streams every swept chunk through `SignatureCarver` (a stub). Implement it:
- **Signatures:** JSON files in `SalvageCore/Sources/SalvageCore/Carving/Signatures/*.json` (SwiftPM resources), each with required `schemaVersion` (1), `id`, `extension`, `category` hint, `header` (hex, with optional `headerOffset`), optional `footer` (hex), optional `maxBytes`, optional `sizeField` (offset/width/endian/adjust for length-prefixed formats). **Unknown fields are ignored, never rejected.** A file with the wrong `schemaVersion` is skipped with a logged reason. Ship an initial set: JPEG, PNG, GIF, HEIC/ISO-BMFF (ftyp), MP4/MOV (ftyp via size field), MP3 (ID3/frame sync), WAV/RIFF, PDF, ZIP (incl. docx/xlsx/pptx), GZIP, 7z, RAR, SQLite, plus generic Office97 (OLE).
- **Engine:** a streaming matcher over chunks (handle matches spanning chunk boundaries with a carry-over window of max header length), sector-aligned header search (configurable, default 512), bounded open-carve count, footer or size-field termination, `maxBytes` fallback. Skip bytes inside **claimed** runs (metadata files) so carving reports only orphaned data. Produce `RecoveredFile`s with `recoveryMethod: .carved`, `filesystem: .carved`, `content: .runs([one contiguous run])`, `isPartial: true` when terminated by `maxBytes`/end-of-extent without footer/size, and an `overwriteConfidence` estimate (0.0 when footer/size validated; 0.6 when partial; 1.0 if the region is internally inconsistent). `fragmentCount` stays 1 (contiguous carving only in v1; fragmented reassembly is out of scope and must be noted).
- **Naming (3.2):** `Reconstructed/<Type>/<type>-<deviceOffsetHex>.<ext>`; collisions are impossible by construction (offset unique); add a sequence suffix if two signatures match one offset. Path shows under `/Reconstructed/<Type>/`.
- **UI:** File Browser groups carved files under a visually distinct "Reconstructed" section within each bucket (EXPERIENCE.md); a "Partial — may be incomplete" text tag (no color); confidence from the existing single function (Medium/Low). Dashboard bucket counts include reconstructed files but show them as "(n reconstructed)".

## Boundaries & Constraints

**Always:** Carving must never emit a file overlapping a claimed metadata run. Work is bounded: cap concurrent open carves (e.g. 64), cap total carved files (e.g. 250k), and never buffer file bodies (only offsets). Validate signature JSON strictly for required fields and hex. Tests: synthetic devices with embedded JPEG/PNG/PDF/ZIP byte patterns across chunk boundaries, inside claimed runs (skipped), truncated (partial), and a wrong-`schemaVersion` + unknown-field JSON fixture. AD-7 floor: assert carved never scores High.

**Never:** No edits to any `Parsers/*.swift`, `ScanSession.swift` (the hook is in place), `ScanEvent.swift`, `RecoveryConfidence.swift`, DiskIO, `ResultsDashboardView.swift` beyond the "(n reconstructed)" caption, or CI. In the app you own `FileBrowserView.swift` and `ResultsViewModel.swift` edits for grouping/tagging; keep them additive. Another agent (lost partitions) adds a dashboard card in a new file and may add a small `volumeFilter` to `ResultsViewModel`; avoid restructuring that type.

## Implementation Notes

- **Schema (AD-6), as shipped:** required `schemaVersion` (1), `id`, `extension`, `category` (one of the `FileCategory` raw values; anything else is rejected, since it names the `Reconstructed/<Type>/` folder), `header` (hex). Optional: `headerOffset`, `alternateHeaders`, `footer`, `footerMode` (`first` | `last`), `footerLength`, `footerSizeField`, `maxBytes`, `sizeField` (one object or an array that is summed; each is `value * scale + adjust`, `scale` being another field with `oneMeans` for SQLite's page size), `segments` (a chained record walk: `start`, `size`, `minimum`, `typeOffset`/`typeLength` with `typeMatch` or `typePrintable`, `largeSize`, `stopAt`, `fillByte`, `zeroSizeToEnd`), `footerOffsetCheck`, `structure` (`gif`), `validate` (`mpegFrames`), `embeds` (ids), `cutsOthers` (default true) and `trustedMaxBytes`. Bounds: every rule together may read at most 64 KiB past a match (`FileSignature.maxReach`), `maxBytes`/`trustedMaxBytes` at most 64 GiB, field widths at most 8; a signature over a bound is skipped with the reason. Hex accepts `?` nibble wildcards (`RIFF????WAVE`). Unknown keys anywhere are ignored, a known key set to `null` counts as absent, and `id`/`extension` are restricted to 1-32 ASCII `[A-Za-z0-9_-]` because they become file names. Files that fail validation land in `SignatureLibrary.skipped` with the reason and are reported with `NSLog` at load; the UI doesn't surface them yet (follow-up).
- **Why `segments` exists:** a footer-only JPEG rule ends at the EXIF thumbnail's own `FFD9`, so camera JPEGs would carve as a few KB. The marker walk (APP0/APP1/... up to `FFDA`) skips embedded data and hands over to the footer search at the scan data, where `FFD9` can only be the real EOI. The same walk gives exact sizes for ISO-BMFF (MP4/MOV/M4A/HEIC) by summing boxes; a sector-aligned JPEG header inside `mdat` is therefore ignored. "MP4 via size field" from the Intent is implemented this way because a single size field only covers the first box.
- **How a carve ends, and the AD-7 evidence it reports:** validated end (footer, size field, record walk ending at the first non-record for walks without `stopAt`, GIF trailer) -> not partial, `overwriteConfidence` 0 -> Medium. Cut by `maxBytes`, by the next sector-aligned header, or by the end of the extent, or a size-field/record-walk size above `trustedMaxBytes` (default 64 MiB; large files are usually fragmented or the field is garbage) -> partial, 0.6 -> Low. Cut by a claimed run (the bytes belong to a live file), a size field that is inconsistent (smaller than the header, larger than `maxBytes`, overflowing), a record walk that meets a non-record before its `stopAt`, or a broken GIF block -> partial, 1.0 -> Low. A walk that reaches the claim or `maxBytes` mid-walk is `.claimed`/`.limit`, never validated; an ISO-BMFF box of size 0 runs to the end of the extent (partial); size 1 reads the 64-bit largesize. `footerMode: last` (PDF) ends at the last footer seen when anything cuts it, so an incrementally updated PDF keeps all its revisions.
- **Next-header rule (revised in review):** a header found while a carve is open ends that carve (partial, `.nextHeader`) and opens its own carve, unless the open carve accounts for it: inside the range its size field/record walk covers, when the header is weak (`cutsOthers: false`) or one the format `embeds` and the covered size is within `trustedMaxBytes` (so a garbage 3 GB box can't hide real files); in the footer search, when it is weak, or embedded and the footer has a `footerOffsetCheck` (ZIP in ZIP); in an open-ended carve, when it is weak and embedded (MP3 frame syncs inside an MP3). Bundled: JPEG embeds JPEG (EXIF thumbnails), MP4/MOV/M4A embed JPEG/PNG (cover art), ZIP embeds ZIP, MP3 embeds MP3; MP3 frame sync and gzip are weak; JPEG's header requires a valid next marker (APPn, DQT, SOFn/DHT, COM, DRI). Concurrent open carves still only share one start offset, so the 64-open-carve cap remains a guard. Open-ended formats (MP3, gzip, OLE, RAR5) end at the next strong header in practice.
- **Naming (3.2):** `<id>-<12 lowercase hex digits of the device offset>.<ext>` under `/Reconstructed/<category displayName>/`; a second signature matching the same offset with the same `id`/`extension` gets `-2`, `-3`. Carved files use `SourceMetadata(filesystem: .carved, volumeOffset: extent start, recordOffset: start, allocationStart: start, contiguous: true, rawRecord: header bytes)`, so `ScanViewModel`'s dedupe key stays unique. The extent start is the offset given to `Carver.beginExtent(offset:length:)` when the caller announces extents, else the first chunk's offset of a contiguous run. Only offsets are kept: `rawRecord` holds at most 64 header bytes.
- **Initial set (19 files):** JPEG, PNG, GIF, HEIC (ftyp heic/mif1/heix/hevc/heim/msf1), MP4 (isom/iso2/mp41/mp42/avc1/M4V/dash/mp71/MSNV/3gpN), MOV (qt), M4A/M4B, MP3 ID3v2, MP3 frame sync, WAV, AVI, PDF, ZIP, GZIP, 7z, RAR 1.5-4 (footer), RAR5, SQLite, OLE2 (.doc). Judgment calls: MP3 frame sync (Layer III, MPEG-1/2/2.5: `FFFB`/`FFFA`/`FFF3`/`FFF2`/`FFE3`/`FFE2`) only counts when the `mpegFrames` check finds two consecutive valid, consistent frame headers (version, layer, bitrate, sample rate, padding give the frame length). MP3, gzip, OLE and RAR5 have no end rule and are always partial/Low; honest, but an OLE FAT walk and an MP3 frame walk would fix two of them (deferred). ZIP covers docx/xlsx/pptx with the `.zip` extension (their first entry doesn't reveal the type). GIF is walked block by block by the engine's `gif` structure walker (a JSON field, `structure: "gif"`, rather than an engine special case keyed by signature id, so a contributed signature can't trigger it by reusing the id); its old `003B` footer matched inside LZW data. ZIP's EOCD only ends a ZIP whose central-directory offset + size equals the EOCD's own offset (`footerOffsetCheck`), so a nested or stray `PK\5\6` doesn't; ZIP64 archives therefore never validate (partial). A JPEG with an MPF secondary image after its EOI loses that image unless the second header happens to be sector-aligned.
- **Sweep interplay:** headers are sought at multiples of 512 device-absolute bytes (configurable in `Limits`), so a partition that isn't sector-aligned still carves at device sector boundaries. Chunks that aren't contiguous with the previous one start a new extent: open carves are cut at the old extent's end (partial) and the carry window is dropped. `Carver.beginExtent(offset:length:)` (default no-op for other conformers) is a hard cut too, so adjacent extents don't merge, and it sets `volumeOffset` for a resumed sweep; `ScanSession` does not call it yet (see Review fixes). A resumed scan carves only the remaining bytes (known limitation, lead to decide). A header not yet examined because it needs bytes from the next chunk bounds how far open carves advance, so a footer past it can't end a carve it would have cut (chunking-independent). `maxCarvedFiles` (250k) stops emission and sets `hitFileLimit`, readable through `Carver.hitFileLimit`; nothing reports that to the user yet (follow-up: the UI should surface it).
- **UI:** `ResultsViewModel.apply` keeps the chosen sort and then moves reconstructed rows after the filesystem's rows; `visibleReconstructedCount` lets `FileBrowserView` render two `Table` sections ("From the filesystem" / "Reconstructed", macOS 14 `Section` rows) only when a listing has carved files. The Name column adds text-only "Reconstructed" and "Partial — may be incomplete" tags beside the existing "Deleted"; the preview pane explains both. Bucket tiles append "(n reconstructed)" to their caption (the only `ResultsDashboardView` line touched); the tile's accessibility label and the dashboard's closing sentence ("indexed from intact metadata") were not changed per the ownership limits and are now incomplete when carved files exist (follow-up). `FileCategory.fromSignature` is still empty: carved names always carry an extension.
- **Out of scope, noted per the Intent:** fragmented reassembly. Every carve is one contiguous run, `fragmentCount` is 1, and a file whose bytes continue after a claimed run is cut there.
- **Review fixes (p3-carving):** the ten review items are fixed in `CarvingEngine.swift`, `SignatureLibrary.swift` and the JSONs, each with a test that fails on the previous engine. The bundled library is found without SwiftPM's `Bundle.module` (which traps when the bundle is missing): a missing resource bundle gives an empty library with a skipped reason.
