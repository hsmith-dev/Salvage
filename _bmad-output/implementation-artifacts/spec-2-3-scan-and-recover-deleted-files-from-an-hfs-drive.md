## Intent

**Problem:** FR-5 includes HFS+ (older Mac drives and Time Machine backups). Discovery recognizes "H+"/"HX" at offset 1024 and routes to `HFSPlusVolume`, a placeholder with `isImplemented = false`.

**Approach:** A bounded, read-only HFS+/HFSX parser in original Swift from Apple's public TN1150, emitting live and deleted regular files with name, path, timestamp and content mapping. Validate against a real `hdiutil create -fs HFS+` image (no sudo) with known live and deleted files.

## Boundaries & Constraints

**Always:**
- **Volume header** (offset 1024, big-endian): signature, version (4 or 5), `blockSize` (512–1 MiB power of two), `totalBlocks` fitting the extent, the fork data of the catalog, extents overflow and allocation files. Reject HFS wrapper volumes ("BD" at 1024) with `unsupportedFilesystem`.
- **B-trees:** parse header node (node size 512–32 KiB, root, leaf links), walk leaves via `fLink` with a visited set and a node-count bound; validate record offsets against the node. Catalog keys: parent CNID + HFS Unicode name (UTF-16BE, decomposed; present as precomposed NFC). HFSX case-sensitive flag is informational.
- **Files:** catalog file records: data fork size and the first 8 extents; **extents overflow B-tree** for more (bounded). Build paths from parent CNIDs with cycle and depth bounds. Emit regular files only (skip folders, symlinks, hard-link indirect nodes under `␀␀␀␀HFS+ Private Data` beyond resolving hard-link files to their indirect node). Timestamps: HFS epoch (1904-01-01 UTC) seconds → `Date`; `contentModDate`.
- **Content:** data fork extents → device-absolute `DataRun`s (`extent.offset + startBlock*blockSize`), truncated at logical size. Resource forks are not emitted. Compressed files (`UF_COMPRESSED` in `bsdInfo.ownerFlags` with decmpfs attribute) → `.unmapped`, noted.
- **Deleted files (best effort, never wrong):** HFS+ deletes remove the catalog record and free the blocks, leaving no catalog trace. Recover from **the journal** (`journalInfoBlock` → journal buffer → transaction blocks that contain older catalog leaf nodes) and from **unused space inside live catalog nodes** (records past `numRecords` that still contain valid catalog file records). A candidate is emitted `isDeleted: true` only if its extents are valid, within the volume, **free in the allocation file bitmap**, and not overlapping another candidate. Bounded work budget per volume. If the journal is absent or unreadable, skip journal recovery and note it.
- Bounds and checked arithmetic as in the other parsers; live corruption fail-closed, candidates skipped.
- Set `isImplemented = true`; update `hfsPlusAndHfsxAreRecognised` in `ScanSessionTests.swift` (that test only) and add positive routing tests in your own file.

**Never:** No edits to other parsers, `ScanSession.swift`, `ScanEvent.swift`, `VolumeDiscovery.swift`, `VolumeScanners.swift`, `Carving/`, the app, DiskIO or CI. No external dependencies. No writes.

## I/O & Edge-Case Matrix

| Scenario | Input | Expected | Error handling |
|---|---|---|---|
| Real hdiutil HFS+ image, live nested files | — | Paths, sizes, mtime; byte-identical content; `.completed` | — |
| File with > 8 extents | fragmented | All extents via overflow tree | — |
| Deleted file from journal / stale node records, blocks free | — | Emitted `isDeleted`, byte-identical | — |
| Deleted, blocks reused | — | Not emitted | Skip |
| HFS wrapper ("BD") | — | `unsupportedFilesystem` | — |
| Bad header / B-tree cycle / oversized node | crafted | `malformed`, bounded | — |

## Implementation Notes

- **Files:** `Parsers/HFSPlusVolume.swift` (actor; `init`/`scan()` signatures unchanged, `isImplemented = true`), `Parsers/HFSPlusStructures.swift` (on-disk structures, fork map, node parsing, limits, stats), `Parsers/HFSPlusJournal.swift` (journal walk). Tests in `Tests/SalvageCoreTests/HFSPlusVolumeTests.swift`: 32 synthetic-image tests, 5 real-image tests built with `hdiutil` in a temporary directory (attached only while populated, detached in a `defer`-style step, directory removed; skipped via `.enabled(if:)` when `hdiutil` cannot create and attach an image), and `realImageSuiteReportsWhyItIsSkipped`, which prints why the real-image suite was skipped and records an issue only when `SALVAGE_REQUIRE_HDIUTIL=1`. `hfsPlusAndHfsxAreRecognised` in `ScanSessionTests.swift` now expects the signature-only stub to reach the parser and fail as `malformed` (empty header), not `unsupportedFilesystem`.
- **Empirical check against TN1150:** a real `hdiutil create -fs HFS+J` image confirmed the journal is in the creating system's byte order (little-endian here, `endian` marker 0x12345678), `bnum` is in `jhdr_size` sectors (512) relative to the volume, the block list header checksum covers its first 32 bytes with the checksum field zeroed, the journal header checksum covers its first 44 bytes (everything before `sequence_num`) the same way, and `binfo[0]` is not a data block: its last 4 bytes (offset 12) hold the transaction's sequence number. macOS sets `BLHDR_CHECK_CHECKSUMS` (flags 3 = check-checksums + first-header), and each data block's checksum is in the same slot of its `binfo` entry, computed over the whole block. Modern macOS zeroes the slack of a catalog node when a record is removed, so on real volumes the journal (older copies of catalog leaf nodes) is the productive source; node slack and freed nodes still work and are covered synthetically. The same image confirmed that a POSIX `12:30.log` is stored in the catalog as `12/30.log`.
- **Scan order:** volume header → extents overflow and catalog headers → allocation map → pass 1 over the catalog leaf chain (`firstLeafNode` → `fLink`, visited set, every node must be a height-1 leaf) collecting folders (CNID → parent, name), the `␀␀␀␀HFS+ Private Data` folder's CNID, which leaf holds each `iNodeNNN` record, every live file CNID (a sorted `[UInt32]`, 4 bytes per live file) and node-slack candidates (in memory only) → pass 2 emits every live file → only then the deleted-file work (journal, freed catalog nodes, bitmap checks, deleted emission). Live emission therefore never depends on deleted-file work. Index nodes are not descended for the catalog, so key ordering is not verified; a duplicate folder CNID, an unknown record type, a broken parent chain, a chain deeper than `maxPathDepth` (2048), or invalid UTF-16 or a NUL in a live name is `malformed`.
- **Deleted-file work is best effort:** the journal harvest and the freed-node scan each run under a wrapper that catches `ScanError.io` and `.malformed` (anything else, including `CancellationError` and `deviceChanged`, propagates), notes the failure in `stats.notes` and skips that source: its candidates are marked conflicted, so they are never emitted but their blocks still count as evidence of reuse. During the deleted evaluation, an unreadable allocation-bitmap page skips the candidates that need it (the page is remembered as unreadable) and the scan completes; an implausible candidate is skipped.
- **What is emitted:** regular files (`fileMode & S_IFMT == S_IFREG`, or mode 0 for records written without BSD info). Skipped: folders, symlinks, directory hard-link aliases (`fdrp`/`MACS`), the hidden `.journal`/`.journal_info_block` files (`jrnl`/`hfs+`), block/char devices, and the indirect-node files themselves. A hard link (`hlnk`/`hfs+`) is emitted under its own name and path with the indirect node's size, modification time, fork and CNID (`allocationStart`); `rawRecord` is the link record followed by the indirect node's record. A link whose indirect node is missing is skipped and counted (`stats.unresolvedHardLinks`), not failed.
- **Names:** decoded from UTF-16BE and presented precomposed (`precomposedStringWithCanonicalMapping`). The catalog stores a POSIX ":" as "/" (Carbon's separator is ":"), so every "/" in a catalog name is shown as ":" before path components are joined with "/"; a ":" in a catalog name cannot be produced through POSIX and is kept as ":". Names containing NUL are rejected (live: `malformed`; deleted: skipped), except the private-data folder's own name. The HFSX case-sensitivity flag is read into the tree header and otherwise unused.
- **Content:** data fork extents (record plus extents-overflow records) → device-absolute runs, coalesced, clipped to the logical size; a size-0 file is `.runs([])`. Overflow records are looked up lazily, per (file ID, first logical block), by descending the extents overflow tree from its root (index nodes: last key ≤ target; heights checked against `treeDepth`), through a small node cache (`maxOverflowCachedNodes`, 32); nothing proportional to the overflow tree's size is kept in memory. Extents shorter than the size, outside the volume, or a missing or empty overflow record are `malformed` for live files. `UF_COMPRESSED` files are `.unmapped`; their size comes from the inline `com.apple.decmpfs` header (read once from the attributes tree, little-endian `uncompressed_size`), falling back to the data fork's logical size (usually 0) when no attribute is found. An unreadable attributes tree is noted in `stats.notes`, not failed, because it only supplies sizes. Resource forks are never emitted.
- **Memory bounds:** leaf walks keep a sparse `Set` of visited node numbers, so their memory follows the nodes actually read, never a (possibly crafted) `totalNodes` (`stats.largestNodeSet` records the peak); pass 1's set is released before pass 2 builds its own, and pass 2's set is the one the freed-node scan uses.
- **Deleted candidates** come from three places: the journal, catalog nodes outside the live leaf chain that still parse as leaves (freed nodes), and the slack between a live node's last record and its offset table (scanned at 2-byte stride for an intact key + 248-byte file record). A candidate must be a regular, non-link, non-compressed file with size > 0, CNID in `16..<nextCatalogID`, a parent that is not root's parent or the private-data folder, extents that are non-overlapping, inside the volume and that account for every block the record claims (`extentBlocks == totalBlocks`, so a deleted file that needed overflow records is skipped rather than mapped partially). One candidate per CNID is kept: the newest copy, ordered by journal sequence number when both copies come from different journal transactions (wrap-aware 32-bit comparison), otherwise by `contentModDate`; copies that can't be ordered and disagree are ambiguous and skipped; a CNID that is still live is skipped. Then every block must be free in the allocation bitmap.
- **Block-reuse evidence:** the extents of every structurally plausible record are registered as claims owned by its CNID the moment it is found — the kept version, every superseded or older version, and records later rejected for an unresolvable parent, a used block, ambiguity, a live CNID, a failed source or the candidate caps. An accepted candidate is dropped when any of its own extents overlaps a claim owned by a different CNID (versions of one file sharing blocks are not an overlap, and a file is not dropped merely because an older version of it overlapped someone else). Example: X frees block 90, Y takes 90–91 and is deleted, live Z reuses 91: Y is rejected (block 91 used) but its claim on 90 drops X. Claims are capped at `maxClaimedRanges` (2,000,000); past the cap, deleted recovery is disabled for the volume because reuse can no longer be ruled out.
- **Stale folders:** folder records found the same way become fallback parents for paths only when no live folder has that CNID. For each such CNID the copy with the latest modification date wins (the later of `contentModDate` and `attributeModDate`, since a rename touches only the latter); copies with the same date that differ in name or parent make the folder unresolvable, so the paths of its deleted children can't be built and those children are skipped like any orphan. Caps: 100,000 candidates / 64 MiB of record bytes, 200,000 stale folders, work budget `4 × totalBlocks + 1,000,000` bitmap checks and stale nodes examined (`stats.deletedBudgetExhausted` when hit).
- **Recovery is disabled** (live scan still runs, `stats.deletedRecoveryDisabled` says why) when the volume header's `kHFSCatalogNodeIDsReusedBit` is set (CNIDs may now point at different folders); on a non-journaled volume, when `kHFSVolumeUnmountedBit` (bit 8) is clear or `kHFSVolumeInconsistentBit` (bit 11) is set (the bitmap may be stale); and on a journaled volume when the journal cannot be shown to be fully replayed: journal info block 0 or outside the volume, an external journal, a journal outside the volume, an I/O error reading the info block or journal header, a bad endian marker, magic or header checksum, invalid header fields, or `start != end`. **This deliberately tightens the frozen "if the journal is absent or unreadable, skip journal recovery" rule** for journaled volumes: an unreadable journal can still hold unreplayed transactions, so the bitmap can't be trusted and no source is used. A journal flagged as needing initialization (its contents are discarded at mount, so nothing can be replayed) or larger than `maxJournalBytes` (1 GiB; its header is still checked) is only skipped as a source (`stats.journal` = `"skipped: …"`), and the other sources proceed. A non-journaled volume reports `stats.journal = "absent"`.
- **Journal walk:** every `jhdr_size`-aligned position in the buffer is probed for a block list header (`max_blocks`, `num_blocks`, `bytes_used`, checksum and the sum of block sizes must all agree), so stale transactions past `end` are harvested as well as current ones. A transaction whose circular span strictly contains `end` was being overwritten by newer ones and is ignored (`stats.journalTornTransactions`); probing then continues one sector on, so the newer headers inside it are still found. When `BLHDR_CHECK_CHECKSUMS` is set, every data block's checksum must match or the whole transaction is ignored (`stats.journalChecksumFailures`). Blocks whose `bnum × jhdr_size` lies inside the catalog file and whose size is a multiple of the node size are split into nodes, and each node is checked on its own: it must map, contiguously and node-aligned, into the catalog's extents below `totalNodes`, or it is ignored. Wrap-around at the end of the buffer is handled; reads go through a two-chunk (1 MiB) cache. Both byte orders are supported and tested.
- **`recordOffset`** is device-absolute: the record's key inside the catalog node for live files, or its position inside the journal buffer / stale node for deleted ones. `allocationStart` is the CNID.
- **Real-image coverage:** nested live files, hard links and symlinks (non-journaled image); `12:30.log` and `a:b/c:d.txt` shown with their colons and read back; a `ditto --hfsCompression` file reported `.unmapped` with its uncompressed size from decmpfs; a 12-extent file produced by filling a journaled 16 MiB image, freeing single blocks and writing into the holes (8 catalog extents + 4 overflow); three deleted files (one in a deleted folder) recovered byte-identical from the journal, while a deleted file whose blocks were reallocated by a filler is not emitted.
