## Intent

**Problem:** FR-5 includes APFS, the format of every modern Mac drive. Discovery already recognizes APFS by signature and routes it to `APFSContainer`, a placeholder with `isImplemented = false`. AD-2 is now ADOPTED: the parser is original MIT-licensed Swift written from Apple's public *Apple File System Reference* (2018+), with no GPL/LGPL code read or copied (not apfs-fuse, libfsapfs, Sleuth Kit, or any port of them).

**Approach:**
1. **Spike first (Story 2.1), on a real volume.** Create an APFS disk image with `hdiutil create -fs APFS` (no sudo), write files with known contents, delete some, unmount, and read the raw device (`/dev/rdiskN`, user-owned) through the parser. Record in Implementation Notes: what was enumerated, what wasn't, and the go/no-go. If the approach is infeasible in reasonable time, stop, document the fallback options explicitly (shelling out to a GPL tool with a FUSE dependency; LGPL linking risk), and report.
2. **Then the parser (Story 2.2):** live files and deleted-but-not-overwritten files with original name, path and timestamp, plus content mapping, through the same unified scan flow.

## Boundaries & Constraints

**Always:**
- **Container (NXSB at block 0):** validate the Fletcher-64 checksum of every object read; reject on mismatch (`ScanError.malformed`). Read `nx_block_size` (4096 typical; accept 4K–64K powers of two), the checkpoint descriptor area, and pick the **latest valid checkpoint** (highest `xid` whose superblock checksums and whose object map is readable). Resolve the container object map (B-tree) to physical blocks. Enumerate `nx_fs_oid[]` volumes.
- **Volume (APSB):** per volume: object map → root tree. Walk the filesystem B-tree: `j_inode_val` (ids, parent, mode, timestamps, size via `INODE_EXT_TYPE_DSTREAM`), `j_drec_val` (directory records, names, hashed variants), `j_file_extent_val` (extents → `DataRun`s, device-absolute: `extent.offset + paddr * blockSize`). Build paths from parent ids with cycle and depth bounds. Emit regular files only; skip directories, symlinks, and the private-dir (`private-dir`, id 3).
- **Bare volume device (APSB at block 0):** when the extent starts with `APSB` (an unlocked volume device read directly, Story 2.4's path), parse it as one volume whose object-map physical addresses are relative to the volume device. Test with a synthetic image; note that a real check depends on 2.4.
- **Encrypted volumes:** if `apfs_fs_flags` lacks `APFS_FS_UNENCRYPTED` (and the container isn't a bare volume), do not try to parse the encrypted trees. Emit `.unlockRequired(device.requiringUnlock(volumeUUID: <apfs_vol_uuid>, volumeName: <apfs_volname>))` where `device` is the init parameter (if nil, build a placeholder `BlockDevice(bsdName: "", displayName: volumeName, sizeBytes: 0, isInternal: false, isBootVolume: false)`), then continue with the next volume. Never fail the scan because a volume is encrypted.
- **Deleted files (best effort, never wrong):** APFS is copy-on-write, so older checkpoints still reference deleted files. Walk **older valid checkpoints** in the descriptor ring (bounded, newest first) and the volume's **snapshots** (`apfs_snap_meta` tree) for inode/drec records absent from the current tree. Emit such a file with `isDeleted: true` only if (a) its full extent list is present and valid, (b) every extent lies within the volume's allocated range, and (c) its blocks are **not in use** by the current checkpoint's space manager bitmaps (parse `nx_spaceman_oid` → chunk-info bitmaps; if the bitmaps can't be read, skip deleted recovery entirely and note it). Two deleted candidates whose extents overlap are both skipped. Use a per-volume work budget as the other parsers do.
- **Timestamps:** nanoseconds since 1970 → `Date`. Size from the dstream's `size` (logical), extents truncated at it; hole regions as `deviceOffset: nil` runs.
- **Compressed files** (`INODE_HAS_UNCOMPRESSED_SIZE` / `UF_COMPRESSED`, decmpfs xattr): emit with correct metadata and `.unmapped` content for now; note it. **Clones** share extents: emit each name; do not treat shared extents as cross-links (reference counts are via the extent-ref tree).
- Bounds: every read through a `read()` limited to the extent, like `FATVolume.read`; cap B-tree depth (≤ 16), node count, key/value sizes; checked arithmetic (`checkedAdd`/`checkedMultiply`/`signed`). Live-tree corruption is fail-closed; deleted-candidate problems are skipped.
- Set `isImplemented = true`; update the routing test `apfsContainerAndBareVolumeAreRecognised` in `ScanSessionTests.swift` (only that test and `pendingFormatPartitionsAreSkippedNotFailed`'s APFS partition), and add positive routing tests in your own file.
- Update `ARCHITECTURE-SPINE.md` AD-2's text to record the spike outcome in one sentence (keep the `[ADOPTED 2026-10-31]` tag). Update PRD Open Question 9's resolution note if the spike changes anything.

**Never:** No edits to `FATVolume.swift`, `NTFSVolume.swift`, `EXTVolume.swift`, `HFSPlusVolume.swift`, `ScanSession.swift`, `ScanEvent.swift`, `VolumeDiscovery.swift`, `VolumeScanners.swift`, `Carving/`, the app, DiskIO or CI. ## Spike Log (Story 2.1, 2026-10-31)

**Setup.** `hdiutil create -size 64m -fs APFS -layout NONE -type UDIF` (no sudo), attached, wrote `hello.txt` (11 B), `docs/big.bin` (3 000 000 B random), `docs/empty.txt`, `docs/nested/mid.dat` (5000 B), `docs/gone.txt` (14 B), `docs/nested/gone-big.bin` (100 000 B); recorded SHA-256 of each; synced; deleted the two `gone*` files; synced; detached. Re-attached with `hdiutil attach -nomount`: `/dev/rdiskN` is `crw-r----- harrisonsmith:staff`, readable without sudo or Full Disk Access, block 0 reads `NXSB`. The exploratory walk was a throwaway probe written only from the layouts in Apple's *Apple File System Reference*; no third-party implementation was read or run.

**What was enumerated.** Block 0 (`nx_superblock`, xid 6, 4096-byte blocks, 16384 blocks); the checkpoint descriptor ring (8 blocks: 4 checkpoint maps + 4 superblocks, xids 3–6, every checksum valid under the Fletcher-64 reading implemented here); the checkpoint maps (spaceman 0x5, reaper 0x11, two free-queue B-trees 0x2/subtype 0x9 as ephemeral objects in the data area); the container object map and its one-leaf B-tree (fixed 16/16 keys, root flag, `btree_info` at the node's end); the volume superblock (`APSB`, `apfs_incompat_features = 0x1` case-insensitive, `apfs_fs_flags = 0x1` unencrypted, volume name, omap, root-tree virtual oid 1028 resolved through the volume omap); the whole filesystem tree at xids 3–6: every inode (parent, private id, mode, `INO_EXT_TYPE_NAME` and `INO_EXT_TYPE_DSTREAM` xfields with 8-byte-aligned payloads), every directory record (hashed keys: `name_len_and_hash`, length including NUL in the low 10 bits), every file extent (`len_and_flags`, `phys_block_num`); the space manager (`blocks_per_chunk = 32768 = 8 × block size`, one CIB, one chunk, bitmap block whose set-bit count equalled `block_count − free_count` exactly); and the main free queue (keys `(xid, paddr)`, value = count, ghost entries meaning 1).

**Content check.** Reading each file's extents from the raw image reproduced all five recorded SHA-256 digests byte for byte, including the two deleted files found only in the xid-3 checkpoint's tree (inodes 22 and 23, parents and names intact).

**What wasn't / surprises.**
- The deleted files' blocks (938, 939–963) are still *set* in the xid-6 bitmap. APFS defers frees: the main free queue held `(xid 4, paddr 938, count 32)`. A literal "free in the bitmap" test would therefore reject exactly the recently deleted files that are recoverable (see Implementation Notes).
- A `Case-sensitive APFS` image (`incompat = 0x8`, normalization-insensitive) also uses hashed directory-record keys; macOS sets at least one of the two flags on every volume it formats, so the plain `j_drec_key_t` variant was not observed.
- Snapshots: none on an hdiutil image (`apfs_snap_meta_tree` empty), so snapshot walking was only exercised synthetically.
- The checkpoint ring is small (8 blocks = 4 checkpoints), so deleted-file recovery through older checkpoints is genuinely best effort: a few more transactions after a delete evict the checkpoint that still lists the file.

**Go/no-go: GO.** Original Swift from the public reference parsed a real macOS-formatted volume end to end on the first attempt, with every checksum validating; nothing in the format forced a fallback. Fallback options (not needed): shelling out to a GPL tool (FUSE dependency, license contamination) or linking libfsapfs (LGPL). The full parser (Story 2.2) was then written and verified against the same kind of image in `APFSRealImageTests`.

## Implementation Notes

- **Files.** `Parsers/APFSContainer.swift` (actor: checkpoint selection, volumes, live walk, deleted recovery, bare volume), `Parsers/APFSObjects.swift` (checksum, `obj_phys`, superblocks, checkpoint maps, object map, inode/extent/snapshot records, space manager), `Parsers/APFSBTree.swift` (node layout, tree info, key comparators, cursor). `init`/`scan()` signatures unchanged; `isImplemented = true`.
- **"Not in use" means "free still pending" (judgment call, revised in review).** The frozen text requires a deleted candidate's blocks to be "not in use by the current checkpoint's space manager bitmaps". The spike showed APFS keeps freed blocks allocated in the bitmap until the deferred free is processed, listing them in the spaceman's main free queue. A block is accepted **only** when (1) it is in the main free queue with a freeing transaction strictly after the candidate's checkpoint xid and no later than the current checkpoint's xid, **and** (2) its bitmap bit is still set. Together these say the free hasn't been processed, so the block hasn't been handed out since it left the candidate. A **clear** bit is *not* accepted: it proves only that the block is free now, not that it wasn't reallocated (to a metadata node or another file) and freed again after the candidate's checkpoint, in which case its contents are someone else's. The earlier note claimed a queued block was "by construction not referenced by any live object and not yet reused"; that held only for the queue half of the rule, and the bitmap-clear half had no such guarantee. Rule (1)+(2) relies on APFS not reusing a block while its free is queued. This **deliberately under-recovers**: once APFS processes the free (bit cleared, queue entry gone), the file is no longer emitted even if its blocks are in fact untouched. If the free queue can't be read, nothing is emitted. Covered by `blocksPendingInTheFreeQueueCountAsFree`, `blockReusedAndFreedAgainIsNotRecovered` (freed/reused/freed again; queued but bit clear; freed in the candidate's own xid; freed after the current xid; control) and the real-image test.
- **Snapshots are walked but cannot yield files.** A file retained by a snapshot still has its blocks allocated and not queued for free, so rule (c) rejects it; snapshot walking only matters for a file whose snapshot has since been deleted, which then no longer appears in the snapshot tree. The walk is implemented as specified (bounded to 64 snapshots, through the current volume omap at the snapshot's xid, superblock at `sblock_oid` verified against the live volume UUID) but is effectively inert. Relaxing (c) for snapshot-held files is a renegotiation, flagged here rather than done.
- **Deleted candidates** are regular-file inodes (id ≥ 16) present in an older checkpoint's tree (same volume UUID, newest first, ≤ 64 superblocks from the ring, skipped when its root equals the live root) but absent from the live tree by exact inode lookup. Deduplicated by inode id (newest wins). Requirements beyond (a)–(c): all extents block-aligned and in logical order, covering the size with no gaps unless the inode has `INODE_IS_SPARSE`, `phys_block_num ≠ 0`, inside `nx_block_count`. Compressed deleted files are skipped (their payload isn't in dstream extents, so nothing could be verified). Size-0 deleted files are emitted with `.runs([])`. Overlap between two candidates' claimed blocks skips both, **container-wide**: candidates from every volume are collected first (volumes share the container's blocks) and overlaps are resolved once before anything is emitted, so deleted files are emitted after all live files. A volume whose budget ran out during collection still contributes its claims to the overlap check, but none of its candidates is emitted. If a later volume's live scan fails, the scan stops before deleted emission, so no deleted files are reported for that scan (under-recovery, never a wrong file); an encrypted volume's deleted files can't be collected and so can't take part in the overlap check. Paths come from the old tree, falling back to the live tree, then `/Orphaned Files`.
- **Budget.** Per volume: `100_000 + 4 × (nodes visited by the live walk)` units; one unit per B-tree node visit during deleted collection, plus `blocks/64 + 1` per bitmap range check (charged to the candidate's own volume at emission). Exhaustion stops deleted recovery for that volume only. Test seam `limitDeletedWork(to:)`.
- **Live tree bounds.** Depth ≤ 16 by rejecting any node level > 16 and requiring each child's level to be exactly its parent's minus one (which also rules out cycles without a visited set); child subtype must match the parent; key/value offsets and lengths are bounds-checked against the table of contents, key area and value area; keys returned by a cursor must not decrease; a hard cap of 2^23 node visits per scan. Every object read is Fletcher-64 verified; a mismatch on anything the live scan needs is `malformed`.
- **Every object is validated against its reference** (a block that checksums can still have been reused). B-tree nodes: a physical node's `o_oid` must equal its block address; a virtual node's `o_oid` must equal the virtual oid and its `o_xid` the transaction in the object-map entry that resolved it; an ephemeral node's `o_oid` must equal its ephemeral oid. Object maps (physical) must have `o_oid` equal to their address; a volume superblock's `o_xid` must equal its container object-map entry's xid. Checkpoint-map blocks and the space manager must have `o_xid` equal to the chosen checkpoint's xid (and the space manager `o_oid == nx_spaceman_oid`). A mismatch is `malformed`: fail-closed on the live path, and in deleted-candidate work the checkpoint, snapshot or space manager concerned is skipped. A stale checkpoint-map block's mappings are ignored. All of these hold on real `hdiutil` images (the real-image tests pass with them). Covered by `hostileTreesTerminateAsMalformed(.wrongIdentity)`, `reusedNodeInAnOlderCheckpointTreeIsNotRead` (root with another oid, root with another xid, leaf with another xid) and `staleCheckpointMapOrSpaceManagerDisablesDeletedRecovery`.
- **Arithmetic on on-disk values.** Every count is bounded before it is used in arithmetic, and the arithmetic is checked. The space manager requires `sm_block_count <= nx_block_count` before deriving chunk, CIB and CAB counts (an `sm_block_count` of `Int64.max` used to trap; `spaceManagerWithAHugeBlockCountIsSkippedNotTrapped`). Deleted-candidate content mapping runs under `attempt`, so a value that doesn't fit is a skip rather than a scan failure, and claim ranges use checked addition. The other expressions in the three files were audited: each is either on values already bounded (4-byte fields, block counts checked against `nx_block_count`, offsets checked against the node or block size) or already checked.
- **Checkpoint selection.** Candidates are every verified `NXSB` in the descriptor ring plus block 0 (same UUID, block size and count), newest first; the first whose container omap also verifies is used. None → `malformed("No valid APFS checkpoint.")`. A tree-based descriptor area (`nx_xp_desc_blocks` high bit) is `unsupportedFilesystem`. The spaceman is read through the checkpoint maps (`cpm_size` honoured, capped at 1 MiB); a Fusion tier-2 device or an unreadable spaceman disables deleted recovery for the scan and records why in `deletedRecoverySkippedReason`. With chunk-info address blocks, the CAB addresses must be distinct, each CAB may list at most `sm_cibs_per_cab` CIBs and the running total at most `sm_cib_count` (checked before anything is appended), and the resulting CIB addresses must be distinct (`chunkInfoAddressBlocksAreBoundedAndNotRepeated`).
- **Directory-record key variant.** Hashed when `apfs_incompat_features` has case-insensitive (0x1) or normalization-insensitive (0x8), else plain; this only affects key ordering, since paths are built from each inode's `INO_EXT_TYPE_NAME` and `parent_id` (names and parents live on the inode), with directory inodes looked up on demand and cached. The private directory (id 3) and other reserved ids (< 16) are excluded by the parent chain.
- **Content mapping.** Runs are device-absolute (`extent.offset + phys × blockSize`), cut at the dstream size, physically adjacent runs coalesced. Holes (`deviceOffset: nil`) only where the format declares them: an inode with `INODE_IS_SPARSE` (logical gaps and a short tail), or an extent with `phys_block_num == 0`, which is a hole for a live file (block 0 is the container superblock, so it cannot be data) and invalidates a deleted candidate. A gap between extents or a short tail in a **non-sparse** live file means the extent list is incomplete, so its content is `.unmapped`, not zero-filled (`gapsAndShortTailsInNonSparseFilesAreUnmapped`).
- **Possible ciphertext is never mapped.** If the volume's object map has `OMAP_ENCRYPTING` (0x2) or `OMAP_DECRYPTING` (0x4), the volume is mid-conversion: any of its blocks may be plaintext or ciphertext, and no per-extent field says which. Every non-empty file is then `.unmapped` (metadata still reported) and deleted candidates are skipped. In a container, an extent with a non-zero `crypto_id` is encrypted under that key, so its file is `.unmapped` (a deleted candidate is skipped). The volume-level `apfs_fs_flags` check alone isn't enough, because it doesn't cover a volume partway through conversion or per-file keys. On a bare volume device, `crypto_id` is expected (the volume was encrypted and the platform has unlocked it, so reads return plaintext), so only the object-map flags apply there (`volumeBeingEncryptedOrDecryptedIsUnmapped`, `extentWithACryptoIDIsUnmappedInAContainerButReadOnABareVolume`, `deletedExtentWithACryptoIDIsSkipped`). Clones (`private_id ≠ inode id`) map through a range scan of the shared stream's extents; each name is emitted. Compressed files (`INODE_HAS_UNCOMPRESSED_SIZE` or `UF_COMPRESSED`) report the uncompressed size with `.unmapped`.
- **Names.** Strict UTF-8; a live inode name that isn't valid UTF-8 or would be an invalid path component ("/", ".", "..") is `malformed` rather than altered. `String(validating:as:)` needs macOS 15, so decoding uses the `UTF8` codec directly.
- **Bare volume (APSB at block 0).** The volume superblock doesn't record the block size; since the checksum covers the whole block, the sizes 4K–64K are tried and the one that verifies wins. As the frozen text says, a bare volume device is the unlocked device read directly, so it is parsed even when `apfs_fs_flags` says encrypted and never emits `.unlockRequired` (an earlier version did, and its test asserted that; both fixed). Object-map entries flagged `OMAP_VAL_ENCRYPTED` are the expected case there and their blocks are read as plaintext on the bare path only; in a container such an entry is still refused (`unsupportedFilesystem`). No space manager means no deleted recovery (reason recorded). Verified synthetically only (`bareVolumeDeviceIsParsedAsOneVolume`, `encryptedBareVolumeDeviceIsReadAsPlaintext`); the real check depends on Story 2.4.
- **`SourceMetadata`:** `recordOffset` is the device-absolute offset of the inode value inside its B-tree node; `allocationStart` is the inode id; `contiguous` means at most one placed run; `rawRecord` is the inode value.
- **Routing tests** updated as allowed: `apfsContainerAndBareVolumeAreRecognised` now expects `malformed` (a bare signature with nothing behind it), and `pendingFormatPartitionsAreSkippedNotFailed` uses an HFS+ stub for its pending partition. Positive routing (whole disk, MBR partition, GPT from hdiutil) lives in `APFSVolumeTests.swift`.
- **Tests.** `APFSVolumeTests.swift`: a synthetic container builder (checkpoint ring, ephemeral spaceman/CIB/bitmap/free queue with per-checkpoint overrides, object maps, volume superblocks, filesystem tree with inode/drec/extent records, optional split trees with a root index node over two leaves for both object maps (fixed-size records) and filesystem trees, object-map and extent encryption flags, bare-volume variant, hostile roots including a cycle through a non-root ancestor index node, and in-place re-checksummed rewrites for crafted objects) behind the synthetic tests (multi-level trees in `multiLevelTreesAreWalkedAndSearched` and `deletedFilesAreRecoveredThroughMultiLevelTrees`; hostile case parameterised ×5), and 2 real-image tests that create disposable `hdiutil` images in a private temp directory, detach them in `defer`/`deinit`, and skip when `/usr/bin/hdiutil` is absent (or `SALVAGE_SKIP_HDIUTIL` is set). The real-image deleted-file assertion relies on the ring still holding the pre-delete checkpoint; on a fresh image this has been reliable, but it is inherently best effort.
