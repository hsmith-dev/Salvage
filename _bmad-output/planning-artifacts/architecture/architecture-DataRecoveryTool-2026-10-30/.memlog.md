- (decision) AD-1 Paradigm: Hexagonal/Ports-and-Adapters, 3 modules -- SalvageCore (domain: filesystem parsers, carving engine, partition reconstruction, recovery-confidence scoring, entities; depends on nothing but Foundation), SalvageDiskIO (macOS adapter: DiskArbitration + raw /dev/rdiskN reads + diskutil FileVault unlock; implements Core's BlockReader port), Salvage app (SwiftUI adapter: UI, FDA prompt, destination writes, update-check). Chosen over a flat 2-layer Core/App split because DiskIO and UI are genuinely independent concerns -- this also gives Open Question 6 (CLI companion) a free path since Core+DiskIO don't depend on SwiftUI. Binds: all FRs. Prevents: disk-access logic leaking into SwiftUI views, UI logic leaking into recovery engine, a future Linux/Windows port requiring Core rewrite (only needs a new DiskIO adapter).
- (question) Dependency direction for AD-1: App -> Core, App -> DiskIO, DiskIO -> Core (to conform to Core's BlockReader protocol). Core depends on neither -- classic hexagonal: Core defines ports, adapters implement them, App is the composition root wiring DiskIO's concrete BlockReader into Core's engine.
- (assumption) AD-2 (highest-risk call, [ASSUMPTION], flag for explicit user confirmation): APFS parsing is implemented as ORIGINAL MIT-licensed Swift code in SalvageCore, informed by Apple's public 2018 APFS Reference + independent testing -- never by linking/vendoring GPL or LGPL parser code (apfs-fuse is GPL-2.0+, libfsapfs is LGPL-3.0/GPL-3.0, Sleuth Kit's license is unconfirmed/mixed per research). Rejected alternative: shell out to apfs-fuse as a separate GPL subprocess (license-safe via process boundary) -- rejected because apfs-fuse is a FUSE driver requiring the user to install macFUSE, a major install-friction/signing complication for a consumer app, and apfs-fuse's own maintenance looks slow (unmerged build-fix PRs into 2025). HFS+/FAT32/exFAT are NOT this risky -- their formats are properly documented (Apple TN1150, Microsoft FAT/exFAT specs), so original MIT implementations there carry normal risk only. This from-scratch APFS parser is the single biggest schedule risk and engineering investment in the whole project (carries forward PRD Open Question 9) -- recommend a timeboxed spike (read-only, unencrypted volume first) before committing further engineering against it.
- (decision) AD-3 (resolves PRD Open Question 10's FR-6/FR-15 tension): FileVault volumes are unlocked via confirmed command 'diskutil apfs unlockVolume <device> -nomount' -- the -nomount flag unlocks without triggering any OS mount, so Salvage never mounts a source volume through the normal Finder/OS path at all (encrypted or not) and the read-only guarantee needs no FileVault-specific exception. After unlock, the now-decrypted block device is read via the same raw-read path as any other device (AD-4). Note: PRD's Open Question 10 speculated 'journal replay on mount' as the risk mechanism -- research found this framing is likely wrong (APFS is copy-on-write, not HFS+-style journaled); the actual mechanism was superseded entirely by choosing -nomount, so this doesn't need further resolution.
- (decision) AD-4 (raw disk access pattern, confirmed real-world precedent via DiskArbitration + dcpomatic/Chromium image-writer pattern): Salvage never reads a device while it remains mounted for normal OS/Finder use. Sequence: DADiskCreateFromBSDName to get a DiskArbitration handle -> DADiskUnmount (whole-disk, for the source) -> open()/read() on /dev/rdiskN (raw/character device, unbuffered) for all scanning. This is enforced at the type level: BlockReader (Core's port) exposes ONLY a read(at:count:) method, no write method at all -- SalvageDiskIO's implementation physically cannot expose a write path to the source disk, making FR-15's read-only guarantee a compile-time property of Core's API, not just a runtime promise.
- (question) Whether Full Disk Access is strictly required (TCC-gated) at the raw /dev/rdiskN level specifically was NOT confirmed by research -- only a vendor (Disk Drill) help page asserts it, no Apple source confirms. Carries forward PRD Open Question 4 unresolved; still needs the hands-on spike before this can be upgraded from assumption to AD.
- (decision) AD-5 (concurrency model, [ASSUMPTION: Swift structured concurrency over Combine/callbacks]): Core uses Swift async/await + AsyncStream exclusively for scanning -- scan() returns an AsyncStream<ScanEvent> (progress updates, found-file events), pause/resume/cancel via Swift Task cancellation, no Combine and no completion-handler APIs anywhere in Core or DiskIO. Binds: FR-2, FR-3. Prevents: UI layer and engine layer independently choosing different async idioms (one using Combine publishers, another using delegates) and the integration seams that creates.
- (decision) AD-6 (carving signature extensibility, ties to PRD Open Question 8 and SM-3 contribution goal): file-format carving signatures are declarative data (JSON definitions: magic bytes, offsets, max size heuristics, file extension) loaded by one generic carving engine in Core -- NOT one hand-written Swift parser subclass per format. Binds: FR-7, FR-8. Prevents: format support becoming an ever-growing set of bespoke code paths that only the original author can safely extend; lowers the bar for a community PR adding a new format to 'add a JSON definition,' directly serving the open-source contribution JTBD.
- (decision) AD-7 (recovery-confidence scoring, resolves PRD Open Question 7's binary floor into a real function): RecoveryConfidence is computed by one pure function in Core, taking a RecoveryMethod (metadata | carved) plus evidence flags (partial-overwrite-detected, fragmentation-detected) and returning the High/Medium/Low enum -- never computed or duplicated in UI code. Binds: FR-12. Prevents: the UI silently diverging from the PRD's binary floor (metadata=High, carved=never-High) by inventing its own display-layer logic.
- (decision) AD-8 (destination safety check, keeps FR-15's volume-identity check out of Core where it doesn't belong): Core's BlockReader port never receives a writable handle to the source -- it has no write method at all, so the type system makes 'Core cannot write to source' structurally true, not just promised. The destination != source volume check (FR-15) is Shell-layer (App) responsibility, using DiskArbitration volume-identity comparison (not path string comparison, which a symlink/bind-mount could fool) before any recovery write begins.
- (decision) AD-9 (lint enforcement for the Core/DiskIO boundary): research confirmed SwiftPM does NOT structurally prevent Core from importing AppKit/DiskArbitration -- it's import discipline, not a compiler boundary. A CI check (e.g. grep/swift-format custom rule forbidding 'import AppKit', 'import SwiftUI', 'import DiskArbitration', 'import IOKit' inside SalvageCore's source tree) enforces AD-1's boundary mechanically rather than relying on code review alone.
