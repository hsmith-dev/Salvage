# Adversarial Review — Salvage ARCHITECTURE-SPINE.md

**Lens:** Attack the spine as an adversary — construct two units one level down that each obey every AD to the letter yet still build incompatibly. Every pair found is a hole to close with a new or tightened AD.

**Verdict:** 12 concrete incompatible-build scenarios found. The spine's ADs are individually sound, but several leave the *shape* of what crosses a module boundary undefined, and a few ADs contradict each other at their seams when each is read literally in isolation. None of these require abandoning the paradigm — each is closable with a tightened Rule or one new AD.

---

### 1. `ScanEvent` has no defined shape

AD-5 commits to `AsyncStream<ScanEvent>` but `ScanEvent` itself is never specified — not even as a sketch of cases. Engineer A (Core) builds it as an enum: `.progress(Double), .found(RecoveredFile), .error(ScanError)`. Engineer B (App, the consumer) is told only "AsyncStream<ScanEvent>" and reasonably assumes a struct with optional fields (`progress: Double?`, `file: RecoveredFile?`, `error: ScanError?`) so a single switch-free `if let` pattern works in SwiftUI. Both satisfy AD-5's literal Rule. The consumer built against one shape won't compile — or worse, will compile against a protocol-erased type and fail at the call site — against the other. **Close with:** a new AD (or an amendment to AD-5) fixing `ScanEvent`'s concrete case list.

### 2. "Pause/resume via Task cancellation" is internally inconsistent

Swift's cooperative cancellation is one-directional — a cancelled `Task` cannot be un-cancelled or "resumed." AD-5's Rule conflates pause/resume with cancellation without saying which. Engineer A implements "pause" as real cancellation plus a persisted resume offset on `ScanSession`, restarting a fresh `Task` on resume (checkpoint-restart model). Engineer B, reading "Task cancellation" as the single sanctioned primitive, instead builds a custom suspend-in-place gate (an actor holding a `CheckedContinuation` the scan loop awaits on pause) so the *same* `Task` resumes — never cancelling at all for a mere pause. These are structurally different control-flow models at the Core/DiskIO seam (one requires DiskIO's raw-read loop to be restartable from an arbitrary byte offset; the other requires it to be suspendable mid-read). **Close with:** an AD distinguishing pause (suspend, same Task) from cancel (terminate, no resume) as two separate, named operations with their own Rules.

### 3. `Signatures/*.json` has no schema contract or version field

AD-6 commits to declarative JSON signature definitions "loaded by one generic carving engine" but fixes no schema, no version field, no compatibility rule. This is precisely the community-contribution surface AD-6 exists to lower the bar for (PRD SM-3) — meaning multiple independent contributors, not just two engineers, will add fields over time. Contributor A adds `"footerBytes"` for trailer-delimited formats. Contributor B adds `"maxFragments"` for carving heuristics. With no schema version or a stated unknown-field policy, the "one generic engine" either silently ignores one contributor's addition (a format that seems to work but doesn't carve correctly) or throws on an unrecognized key (breaking every future contribution that doesn't exactly match the first author's ad hoc shape). **Close with:** an AD fixing the signature JSON schema (even minimally: required fields, a `schemaVersion` field, and "unknown fields are ignored, not rejected") — this is exactly the kind of "two units diverge incompatibly" case AD-6 was meant to prevent, one level too shallow.

### 4. `RecoveredFile` ↔ `LostPartitionCandidate` has no modeled relationship

The ERD relates `BlockDevice ||--o{ LostPartitionCandidate` and `ScanSession ||--o{ RecoveredFile`, but nothing connects a `RecoveredFile` back to the `LostPartitionCandidate` it was recovered from. FR-9's own testable Consequence requires lost-partition results to "never merge with or appear inside the normal mounted-volume results list" as a *distinct UI category* — a data-level requirement the entity model doesn't support. Engineer A adds `sourcePartition: LostPartitionCandidate?` to `RecoveredFile`. Engineer B instead adds a `targetKind: .mountedVolume | .lostPartition` discriminator to `ScanSession` and expects the UI to partition all of a session's `RecoveredFile`s by that single flag. Same requirement, two incompatible data shapes — and the Capability Map compounds this by placing both normal and lost-partition parsing in the same `SalvageCore/Parsers` area with no note of the distinction. **Close with:** an explicit relationship in the ERD (even a nullable FK is enough to fix the shape).

### 5. No concurrency rule for two `ScanSession`s targeting one `BlockDevice`

AD-4 fixes the unmount-before-read sequence per scan, but nothing governs what happens if two sessions target the same device at once — a real near-term risk given the Deferred section's own CLI-companion ambition (App + a future CLI running concurrently against the same drive). The ERD's `ScanSession ||--|| BlockDevice` cardinality notation reads as 1:1, but that's a diagram convention, not an enforced invariant. Engineer A (DiskIO) assumes nothing above it will ever construct two sessions for one device, so builds no lock. Engineer B (Core) assumes DiskIO enforces single-session-per-device at the `DADiskUnmount` layer, so builds no guard either. Neither layer owns the invariant; a second concurrent scan silently corrupts both sessions' reads (two `DADiskUnmount` calls, two raw-read cursors on the same device). **Close with:** an AD naming which layer owns the single-session-per-device lock.

### 6. FileVault unlock timing relative to scan start is unspecified

AD-3 fixes *how* unlock happens, not *when*. FR-6 implies unlock-before-scan for an already-known encrypted volume, but a lost partition (FR-9) that turns out to be encrypted APFS is discovered mid-scan, not up front — there's no candidate to prompt-unlock before the scan even starts. Engineer A (Core) designs the scan loop to yield a `ScanEvent.unlockRequired(BlockDevice)` case mid-stream and await resolution before continuing — meaning the `AsyncStream` itself must support an interactive pause-for-input. Engineer B (App), having only ever seen AD-3/FR-6 framed as a pre-scan step, builds a single up-front "inspect devices, prompt for any FileVault volumes, then start the scan" phase with no code path for an unlock prompt arriving after `AsyncStream<ScanEvent>` has already started. The lost-partition-plus-FileVault case (a real, not edge, scenario given FR-6 and FR-9 are both v1-committed) has no agreed integration contract between these two builds. **Close with:** an AD stating whether unlock-mid-scan is supported, and if so, adding `.unlockRequired` to the `ScanEvent` shape fixed in finding #1.

### 7. AD-7's "evidence flags" have no fixed representation or producer

AD-7's confidence function takes "evidence flags (partial-overwrite-detected, fragmentation-detected)" but nothing says whether these are booleans, counts, or severities, or which code (the carving engine, AD-6, vs. the metadata parser, AD-2) is responsible for computing them. The Deferred section explicitly expects the Medium/Low boundary to be refined later "once real carved-file test cases inform it" — which is impossible if the carving engine only ever emits a boolean `fragmentationDetected: Bool` (no way to later distinguish "slightly fragmented" from "severely fragmented" without a producer-side format change). Engineer A (carving engine) ships booleans because that's what AD-7's Rule literally lists. Engineer B (confidence function, written later per Deferred) needs graduated evidence to do the Medium-vs-Low work the PRD assigned it and discovers the producer can't supply it. **Close with:** fixing evidence-flag types (e.g. `fragmentCount: Int`, not a bool) now, before the carving engine's output shape calcifies.

### 8. AD-1 and AD-8 disagree about who's allowed to call DiskArbitration

AD-1's prose names `SalvageDiskIO` as *the* macOS adapter for DiskArbitration. AD-9's Rule, though, only forbids the literal import strings inside `SalvageCore`'s source tree — it says nothing about the `Salvage` app target. AD-8's Rule then explicitly says "the app layer using DiskArbitration volume-identity comparison" for the destination-safety check. Engineer A reads AD-1's intent and assumes AD-8's "app layer... using DiskArbitration" really means "via a method `SalvageDiskIO` exposes to the app." Engineer B reads AD-8 literally and writes `DADiskCopyDescription` calls directly inside `RecoveryDestinationWriter.swift` in the `Salvage` target, since AD-9 never forbids DiskArbitration imports there. Now two independent, unsynchronized integration points with the same Apple framework exist, defeating AD-1's stated adapter-isolation purpose (e.g. divergent options passed to `DADiskCreateFromBSDName`, divergent error handling for the same framework calls). **Close with:** either route AD-8's check through a `SalvageDiskIO` API, or extend AD-9's CI check to cover the `Salvage` target too and say so explicitly.

### 9. `ScanSession` has no way to target a specific `Volume`, only a whole `BlockDevice`

FR-1 covers "any mounted or recognized block-device storage device," and real recovery scenarios commonly target one partition/volume on a multi-volume disk, not the whole raw device. But the ERD only models `ScanSession ||--|| BlockDevice : targets` — there's no relationship from `ScanSession` to `Volume` at all. Engineer A (App, device-selection UI) assumes the user can pick a specific mounted `Volume` and that selection gets passed down somehow, perhaps as a volume-offset parameter bundled into the `BlockDevice` reference. Engineer B (Core, consuming `ScanSession.targets`) only ever receives a `BlockDevice` per the fixed ERD relationship and has no field to know whether "scan the whole device" or "scan just this one volume's extent" was intended — so builds whole-device-only scanning, silently dropping the volume-level targeting FR-1 implies is possible. **Close with:** either an explicit `Volume` relationship on `ScanSession`, or an AD stating volume-level targeting is out of scope for v1 (currently neither is said).

### 10. `UnlockError`'s delivery path into the UI is unspecified

The Consistency Conventions table fixes `UnlockError` as part of the shared `SalvageError` hierarchy, with distinct cases for wrong-password vs. tool/version drift (FR-6's own testable Consequence). But nothing says whether `UnlockError` surfaces through `ScanEvent` (requiring `ScanError` to wrap or convert it — see finding #1/#6) or through a separate, non-streamed `async throws` call made before a `ScanSession` ever starts. Engineer A makes `ScanError` an enum with a `.unlockFailed(UnlockError)` case, routing everything through the single `AsyncStream<ScanEvent>` channel. Engineer B treats unlock as a precondition entirely outside the stream (`func unlock(_:) async throws` called by the App before constructing a `ScanSession`), so `UnlockError` never touches `ScanEvent` at all. Both "use the `SalvageError` hierarchy" per the Conventions table; their actual wiring is incompatible, and FR-6's wrong-password-vs-drift distinction has no single place it's guaranteed to reach the UI. **Close with:** fixing this as part of the same AD that resolves finding #6.

### 11. No atomicity/partial-failure contract for destination writes

FR-16's Consequence (governed by the spine's own Capability Map, Scan Results & Recovery UI row) requires the shown file count/size to reflect what was *actually written*, "not the pre-recovery selection count, if any copy failures occurred" — meaning partial failure is an explicitly anticipated case. No AD specifies whether `RecoveryDestinationWriter` (AD-8's home) writes sequentially with per-file success/failure reported back, or as a single batch operation. Engineer A builds a sequential loop yielding per-file completion the UI accumulates into the final tally (supports FR-16 directly). Engineer B builds `copyAll(files:) async throws -> RecoveryResult`, all-or-nothing — a single thrown error loses exactly the per-file granularity FR-16 requires, and there's no AD forcing the correct choice. **Close with:** an AD (or an addition to AD-8) fixing per-file result reporting as the Rule.

### 12. AD-9's CI check doesn't cover transitive dependencies

AD-9 greps `SalvageCore`'s *own* source tree for forbidden import strings — it says nothing about a third-party Swift package `SalvageCore` might legitimately depend on (e.g., a future JSON-schema-validation package needed to close finding #3) that itself transitively pulls in `AppKit` or platform-specific code. Engineer A adds such a dependency to `SalvageCore`'s `Package.swift` without auditing its own dependency graph; AD-9's CI check passes (it only scans files physically under `SalvageCore`'s tree); the "portable Core, ready for a Linux/Windows DiskIO adapter" promise that's the entire stated reason for AD-1's module split is silently broken, with no AD or CI check ever firing to catch it. **Close with:** extend AD-9's Rule to also assert (e.g. via `swift package show-dependencies` or a resolved-manifest check) that no transitive dependency of `SalvageCore` requires a non-Linux/Windows-portable platform framework.
